# HAP 包体瘦身：151.6 MB → 71.8 MB（-53%）

> 鸿蒙 App 里嵌了 Node 运行时（`libnode.so` 120.9 MB）+ 一百多 MB 的 JS 载荷，
> 打出来的 HAP 一开始 **151.6 MB**。这篇文章记录**怎么砍到 71.8 MB**，
> 以及其中一个我**踩了三次才找对位置**的配置项。
>
> 全部数字来自实测（`zip` 中央目录分析 + 产物 `Get-Item`），不是估算。

---

## 结论先给

**一个字段，减半体积：**

```json5
// entry/src/main/module.json5
{
  "module": {
    "pages": "$profile:main_pages",
    "compressNativeLibs": true,     // ★ 就是它
    "extractNativeLibs": true
  }
}
```

| 条目 | 压缩前 | 压缩后 |
|---|---|---|
| `libnode.so` | 120.9 MB | **43.0 MB**（DEFLATE，压到 1/2.8） |
| `libc++_shared.so` | 1.2 MB | 0.4 MB |
| `dsh-payload.tar.gz` | 28.1 MB | 28.1 MB（本身已 gzip，无空间） |
| **HAP 总大小** | **151.6 MB** | **71.8 MB（-53%）** |

**并且验证过：安装后系统会解压 `.so`，`dlopen` 照常工作** ——
也就是说这不是"压了但用不了"的假优化。

---

## ★ 我踩了三次的坑：这个字段该写在【哪一层】

`compressNativeLibs` 是 **`module.json5` 的 module 级属性**。

我按直觉试过的三个位置 **全部被 schema 拒绝**：

| 尝试 | 位置 | 结果 |
|---|---|---|
| ① | `build-profile.json5` 的 `buildOption` | ✗ `Schema validate failed` |
| ② | `build-profile.json5` 的 `buildOption.nativeLib` | ✗ `Schema validate failed` |
| ③ | `build-profile.json5` 的 `buildOptionSet[].arkOptions` | ✗ `Schema validate failed` |
| ✓ | **`entry/src/main/module.json5` 的 `module` 级** | ✅ 生效 |

**最坑的地方**：schema 校验**只告诉你"哪个键不对"，不告诉你"该写到哪"**。

### 方法论（比结论更值钱）

遇到 `Schema validate failed` 时，**别猜，去 schema 文件里搜这个键**：

```
<DevEco>/sdk/default/openharmony/toolchains/configcheck/configSchema_rich.json
<DevEco>/sdk/default/openharmony/toolchains/modulecheck/module.json
```

搜到它出现在**哪个对象下**，就知道该写在哪一层。
**这比反复试位置快得多** —— 我试了三次才想到这个办法。

## 怎么验证"真的压了"（不是看 HAP 大小就完事）

只看总大小会骗你：可能只是某个条目变小，也可能产物根本没重打。

**正确做法：直接读 HAP（zip）的中央目录，逐条目看压缩方法。**

```bash
# 列出 HAP 内每个条目的压缩方法（0=STORED 未压缩，8=DEFLATE）
python -c "
import zipfile
z = zipfile.ZipFile('entry-default-signed.hap')
for i in z.infolist():
    m = 'STORED' if i.compress_type == 0 else 'DEFLATE'
    print(f'{m:8} {i.compress_size/1048576:8.1f} MB  {i.filename}')
"
```

**优化前**（这是我实际看到的）：

```
STORED    120.9 MB  libs/arm64-v8a/libnode.so      ← 一点没压
STORED      1.2 MB  libs/arm64-v8a/libc++_shared.so
STORED     28.1 MB  resources/rawfile/dsh-payload.tar.gz
```

**优化后**：

```
DEFLATE    43.0 MB  libs/arm64-v8a/libnode.so      ← 压到 1/2.8
DEFLATE     0.4 MB  libs/arm64-v8a/libc++_shared.so
STORED     28.1 MB  resources/rawfile/dsh-payload.tar.gz   ← 已 gzip，压不动（正常）
```

**判据**：`libnode.so` 那行的第一个字段必须是 `DEFLATE`。

## 三个"别浪费时间"的结论

### 1. `llvm-strip` 对 Node 官方产物收益为 0

我试过对 `libnode.so` 跑 `llvm-strip`：**体积减少 0%**。
原因：**Node 官方发布产物已经 strip 过了**。

**⇒ 别在 strip 上花时间**，省空间的正确手段是"压缩"（上面那个字段）或"删插件"。

### 2. hvigor 会排除点文件（无害，但会误导你的核对）

把 11419 个文件的载荷放进 `resources/` 后，HAP 里只有 **11337** 个 —— 少 82 个。

逐一核对后确认：**被排除的全是点文件/点目录**，没有一个是运行时代码：

```
38  node_modules/node-domexception/.history      编辑器本地历史
 5  @mixmark-io/domino (.gitmodules/.mocharc.json/.nvmrc/.yarn/…)
 4  fast-uri/.github      CI workflows
 4  compression/…/debug   (.coveralls.yml/.eslintrc/.npmignore/.travis.yml)
 余下：.npmignore / .travis.yml / .eslintrc / .gitattributes / .editorconfig / .keep
```

**⇒ hvigor 排除点文件是合理行为。**
**但核对时要直接查 HAP，不要只看磁盘** —— 否则你会以为"打包丢了文件"。

### 3. 想再小，只有三条路

| 手段 | 收益 | 代价 |
|---|---|---|
| 删掉用不到的插件/资源 | 取决于内容 | 功能缺失 |
| 首启下载大载荷 | 可省几十 MB | **违反"离线可用"** |
| 换更小的运行时 | 取决于构建选项 | 兼容性风险 |

`libnode.so` 的 43 MB（压缩后）是**硬成本** —— 它是真正的 V8 + Node 核心。

## 附带：两个和体积无关但一起踩到的打包坑

### ① native 产物必须落到 `entry/libs/<abi>/`

CMake 里**必须显式设输出目录**：

```cmake
set(CMAKE_LIBRARY_OUTPUT_DIRECTORY
    ${CMAKE_CURRENT_SOURCE_DIR}/../../../libs/${OHOS_ARCH})
```

**不设它，native 产物落在 `build/` 下，HAP 里就【没有 `libs/` 目录】** ——
表现为"装上了但功能不通"，而且是**不报错的那种**。

### ② `.so` / `.node` 没签名，商用机上装上也用不了

鸿蒙商用版对 ELF 做**代码签名校验**，没有 `.codesign` section 直接不可用。

```bash
$SDK/ohos-sdk/linux/toolchains/lib/binary-sign-tool sign \
  --in-file libnode.so --out-file libnode.signed.so --selfSign 1
```

**⚠ 注意顺序：要【在 strip 之后】签。** 先签后 strip 会把签名信息抹掉。
