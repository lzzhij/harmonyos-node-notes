# 鸿蒙端侧常驻与子进程：三条路的实测死法

> 目标：让 App 里的服务**在切后台/锁屏后继续活着**，以及**崩了能自动重启**。
> 结论：**在这台设备（Mate 70 / HarmonyOS 7 / API 26）上，这两件事都做不到。**
> 下面是我实际调用的 API、设备返回的**原文错误码**，以及为什么每条都堵死。
>
> 写这篇文章是因为中文资料里几乎查不到这些错误码 —— 而它们能替你省掉两周。

---

## 结论先给（省时间版）

| 想做的事 | 结论 | 设备返回的原文 |
|---|---|---|
| 后台无限常驻 | ❌ 做不到（普通应用） | `9800005 Continuous Task verification failed. Current device can not request continuous tasks of the TASK_KEEPING type.` |
| 进后台后再申请长时任务 | ❌ 不允许 | `9900002 Transient task verification failed. Request is not allow after the preset time of entering background.` |
| 用子进程跑 Node（崩了能重启） | ❌ 这台设备不支持 | `Capability not support. (code=801)` |
| 读用户目录（如下载/文档） | ❌ 本机不支持 | 801 / `EPERM: opendir '/storage/Users/currentUser'` |
| 延长后台存活 | ⚠️ 部分可行 | `requestSuspendDelay` 可用，把约 90 秒延长到 **3~4 分钟** |

**一个贯穿性的规律**（值得记住）：

> **鸿蒙很多"新能力"是「SDK 里有声明、具体设备未实现」。**
> 看声明文件只能证明它**存在**，不能证明它**可用** —— **必须真机试一次才能定论。**

---

## 一、`801` 是什么：SDK 有、设备没有

### 实测过程

`@ohos.app.ability.childProcessManager` 在 SDK 声明里**确实存在**
（含 `startChildProcess` / `startArkChildProcess` / `startNativeChildProcess`，
以及 `ChildProcessArgs` / `ChildProcessOptions` 等类型，`isolationUid` 可跑独立 uid）。
看起来"崩了能重启的看门狗"有着落了。

于是我加了一个最小探针：

```ts
// ArkTS 侧：用 try/catch 包住，失败也不影响 App 启动
try {
  const pid = await childProcessManager.startArkChildProcess(
    './ets/process/ProbeProcess.ets',
    { entryParams: 'probe' }
  );
  hilog.info(0x0000, 'probe', '子进程 pid=%{public}d', pid);
} catch (e) {
  hilog.error(0x0000, 'probe', '子进程启动失败: %{public}s', JSON.stringify(e));
}
```

子进程文件继承 `ChildProcess` 并实现 `onStart(args)`，里面只打一条 hilog。

### 设备返回

```
Capability not support. (code=801)
```

**并且 hilog 里完全没有子进程入口的任何日志** —— 说明它压根没进到子进程代码，
在能力检查阶段就被拒了。

### 三层要分清

| 层次 | 结论 |
|---|---|
| API 是否存在 | ✅ **存在**（SDK 声明文件确认，类型齐全） |
| **这台设备是否支持** | ❌ **不支持**（801） |
| 所以能力上 | ❌ "把 Node 放进子进程 ⇒ 崩了能重启"与"进程外看门狗"**在这台设备上做不到** |

### 801 在本项目里出现多次，含义统一

- `getUserDownloadDir()` / `getUserDocumentDir()` → **801**（设备不支持该 API）
- 权限申请 `authResults=[2,2]`（2 = **不受支持**）
- `childProcessManager.startArkChildProcess` → **801**

**⇒ 看到 801，第一反应应该是"换个设备试"或"换条路"，而不是"我代码写错了"。**

### 一个重要教训：不要用 `process.pid` 拿子进程 pid

ArkTS **没有** Node 的 `process` 对象，写了会直接编译报错
`Cannot find name 'process'`。子进程 pid 要从 `startArkChildProcess` 的**返回值**拿。

## 二、后台常驻：三个错误码，两条死路，一条半活路

### 死路 1：`TASK_KEEPING` 长时任务 → 9800005

```ts
// 期望：声明长时任务，带通知，锁屏后继续跑
await backgroundTaskManager.startBackgroundRunning(
  ctx, backgroundTaskManager.BackgroundMode.TASK_KEEPING, wantAgentObj
);
```

设备返回：

```
9800005 Continuous Task verification failed.
Current device can not request continuous tasks of the TASK_KEEPING type.
```

**⇒ 本机（手机）不支持该类型。** 平板/车机可能有不同结果 —— 但我只能说这台不行。

### 死路 2：`DATA_TRANSFER` → 9900002（且时机有硬要求）

```ts
await backgroundTaskManager.startBackgroundRunning(
  ctx, backgroundTaskManager.BackgroundMode.DATA_TRANSFER, wantAgentObj
);
```

设备返回：

```
9900002 Transient task verification failed.
Request is not allow after the preset time of entering background.
```

**这条错误信息本身极有价值**：它说的不是"你不支持"，而是**"你来得太晚了"** ——
**进入后台超过预设时间后，就不允许再申请**。

**⇒ 要申请长时任务，必须在【进入后台之前】申请。** 这是我踩出来的时机约束。

### 另一个坑：`backgroundModes` 的写法已经变了

`module.json` 里写字符串数组的老写法**在新版 API 上已被移除**：

```json5
// ✗ 旧写法：schema 校验失败
{ "module": { "backgroundModes": ["dataTransfer"] } }
```

报错是 `instancePath:'module' / propertyNames:'backgroundModes'` 失败，
而且 `if/then` 还要求配套 `ContinuousTaskExtensionAbility`。
**也就是说：想真的做长时任务，你得实现一个配套的扩展能力，不是加个字段就完事。**

### 半条活路：`requestSuspendDelay`（值得留着）

```ts
const delay = backgroundTaskManager.requestSuspendDelay('保持连接', () => {
  // 回调到期后可以续期
  backgroundTaskManager.getRemainingDelayTime(delay.requestId).then(t => { /* … */ });
});
```

**实测：可用，且到期后回调确实触发了、确实能续。**
效果：把切后台后的可用时间从约 **90 秒**延长到约 **3~4 分钟**。

**成本极低（几行代码），值得保留** —— 但它**不能无限续**。

### 结论

1. **普通应用在鸿蒙上无法无限常驻后台。** 真正常驻必须实现 `ContinuousTaskExtensionAbility`（配套扩展能力）。
2. **要申请长时任务，必须在【进入后台之前】申请**（9900002 的教训）。
3. **最可靠的"常驻"是把 App 保持在前台** —— 可用 `power-shell timeout -o <ms>` 覆盖熄屏时间。
4. `requestSuspendDelay` 值得保留：成本低，把可用时间延长到 3~4 分钟。

## 三、还有两条与"活着"相关的实测限制

### `flock(2)` 不支持

```
flock is not supported on openharmony-arm64
```

大量 Node 生态用 lockfile 做"单实例互斥"。**在鸿蒙上，单进程场景直接视为"总是获取成功"** 即可。

### 不能 spawn 任何外部程序

`/bin/sh` 与 `/system/bin/sh` **都存在**，但：

```
spawnSync → EACCES
```

**⇒ seccomp 禁止 app 执行外部程序。** 推论：

- 依赖 `spawn` 的工具（如 ripgrep）**全部不可用**；
- 需要它们的场景只能**用纯 JS 复刻其输出契约**（我实测复刻过 `rg` 的 `--json` NDJSON 格式，可行）；
- **别指望 shell 工具** —— 端上 agent 的"手"只能是纯 Node 的文件/网络工具。

## 四、一张表带走

| 现象 | 真因 | 该怎么办 |
|---|---|---|
| `code=801` | 该 API 本设备未实现 | 换设备试 / 换路；**别改代码** |
| `9800005` | 该长时任务类型本机不支持 | 换类型或放弃无限常驻 |
| `9900002` | 进后台超时后才申请 | **必须在进后台之前申请** |
| `requestSuspendDelay` 到期 | 只延长不永久 | 保留它（值 3~4 分钟），但别指望永驻 |
| `flock is not supported` | 无 flock | 单进程视为总是成功 |
| `spawnSync → EACCES` | 禁止执行外部程序 | 纯 JS 复刻工具的输出契约 |
| `EPERM: opendir /storage/...` | 沙箱外目录不可读 | 把 `HOME` 指到沙箱内；读用户文件走系统文件选择器 |

**最后再强调那条规律**：鸿蒙生态里"声明存在"与"设备可用"是两件事。
我在这篇文章里花的每一小时，都是因为一开始把前者当成了后者。
