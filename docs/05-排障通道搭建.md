# 开发期最大的敌人不是崩溃，是「看不见」

> 在鸿蒙上调试一个进程内 Node 运行时，我花在"搭观测通道"上的时间，
> **比花在改代码上的时间还多** —— 而且这是对的。
>
> **每一次盲猜的改动，成本都远高于搭一条通道。**
> 这篇文章记录我搭起来的四条通道，以及**为什么沙箱日志读不到**。

---

## 核心结论

**沙箱里的日志文件，连 debug 签名的应用也不让 `hdc` 读**（实测 `permission denied`）。

这一条会毁掉很多人的第一小时 —— 因为直觉是"日志写在文件里，我去拉出来看"。
**拉不出来。** 于是必须换通道。

---

## 四条通道（缺一不可）

| 通道 | 命令 | 用途 |
|---|---|---|
| **① 看屏幕** | `hdc shell snapshot_display -f /data/local/tmp/s.jpeg` + `hdc file recv` | 自己看 UI 状态，**不依赖任何日志** |
| **② 点屏幕** | `hdc shell uitest uiInput click <x> <y>` | 自己操作 UI（能自己走完流程） |
| **③ 日志回传** | 端上 POST 到电脑：`hdc rport tcp:19999` + `127.0.0.1:19999` | **完整不截断**的日志 |
| **④ 端口映射** | `hdc fport tcp:15577 tcp:5577` + `curl` | 端到端验证服务真的可用 |

**每加一条通道，定位速度就上一个台阶。**

### ① 截图：最被低估的通道

```bash
hdc shell snapshot_display -f /data/local/tmp/s.jpeg
hdc file recv /data/local/tmp/s.jpeg ./
```

**为什么它最重要**：它**绕过整个日志系统**。
应用崩溃、ANR、白屏时，截图是唯一还活着的观测手段。

**配套做法（强烈建议）**：**把界面当调试台** —— 把 `typeof 模块`、状态机当前值、
以及 `node-boot.log` / `node-stdout.log` 的**尾部**直接刷到 UI 上。
一张截图就能定位，省掉大量来回。

### ② `uitest uiInput`：能自己走完流程

```bash
hdc shell uitest uiInput click 500 1200      # 点
hdc shell uitest uiInput keyEvent 2050       # 空格（见下面坑）
```

**两个坑**：

1. **`uitest` / `snapshot_display` 只作用于【前台应用】。**
   用户手机上开着别的应用时会抢前台，表现为"点了完全没反应"。
   ⇒ **每次操作前先确认前台**（`hdc shell aa dump -l` 或直接截图看）。
2. **`hdc shell` 会把引号剥掉** ⇒ 带空格的文本必然被设备 shell 拆成多参数。
   ⇒ **解法**：逐词 `uitest uiInput text <词>`，词间插空格键事件（`keyEvent 2050`）。

### ③ 日志回传：唯一"完整不截断"的通道

因为沙箱文件读不到（见开头），**让应用主动把日志发出来**：

```bash
hdc rport tcp:19999        # 把电脑的 19999 反向映射到设备
```

端上（ArkTS 或 Node）用 `http` POST 日志到 `127.0.0.1:19999`，电脑侧起个最简单的接收端即可。

**为什么不用截图读日志**：截图里的长数字**会被截断** ——
我实测把 `36,305,644` 读成了 `3,630,564`，差点据此做出错误判断。
⇒ **打体积用 MB 保留一位小数，或分段打印**；**长内容必须走通道 ③**。

### ④ `hdc fport`：最硬的端到端证据

```bash
hdc fport tcp:15577 tcp:5577
curl http://127.0.0.1:15577/facts
```

**这条通道的价值**：它证明的是**"服务真的在端上跑着并响应"**，
而不是"日志说它启动了"。**日志会是假的，curl 不会。**

我的 `/facts` 接口就返回这种东西：

```json
{ "node": "v24.2.0", "platform": "openharmony", "arch": "arm64",
  "execArgv": ["--expose-internals","--jitless","--no-verify-heap"],
  "native": { "internalModules": true,
              "koffi": "not-loaded(MODULE_NOT_FOUND)",
              "node-pty": "not-loaded(MODULE_NOT_FOUND)" } }
```

**这一条 JSON = 一次真机成功运行的证书。**

## 反面模式：三个我踩过的"假信号"

### 假信号 1：hilog 里没有我的日志 ⇒ 以为代码没执行

**错的。** 应用侧 `INFO` 级别日志**经常不进 hilog 的 dump 缓冲**。

**对策**：**关键信息必须同时打 hilog，并且用能进缓冲的级别**；
判断"是否执行到"**不要依赖 hilog 有没有那行**，改用截图或回传通道。

**推论**：native 侧（C/C++）的关键信息**必须同时打 hilog** ——
哪怕在崩溃信号处理器里，虽然信号上下文不严格安全，**但那是唯一出路**。

### 假信号 2：`VmSize` 很大 ⇒ 以为 V8 起来了

**错的。** ArkTS/ArkWeb **自己就占约 40 GB 虚拟地址空间**。
拿 `VmSize` 当"V8 起来了"的证据，会得出完全错误的结论。

**对策**：用**功能性判据**（服务能响应、`typeof` 正确），不要用资源计数。

### 假信号 3：点击"看起来生效了" ⇒ 其实没生效

**判断"某个点击是否生效"，最可靠的是【前后两次 `dumpLayout` 的差异】** ——
比看截图或猜坐标强得多。

我实测过一个案例：界面上有个「选择工作区」标签，点它**没有任何反应**；
把两次 `dumpLayout` 的节点按坐标逐一对比，发现**布局一字未变** ⇒ 确认无效。
而点它**正下方**的 workspace 那一行 ⇒ 布局整体上移、多出新节点 ⇒ 生效。

**方法论**：**要证明一个动作生效，就要有一个"动作前/后"的可比快照。**
截图是给人看的，`dumpLayout` 差异是给判断用的。

### 附带一条：带确认按钮的对话框，不要用系统返回键

`keyEvent Back` 在很多 UI 里只表示**"取消/关闭"**，**不等于"确定"**。
用它关掉窗口后，界面会一直停在原状态，**表现为"发了消息完全不动"** ——
极易误判成后端故障。

**判据**：**先找窗口里有没有「确定/打开/完成」这类按钮**，有就点它。

## 一张检查清单：当你"什么都看不见"时

```
□ 前台是哪个应用？（uitest/snapshot 只作用于前台）
□ 截图里现在是什么？（通道 ①）
□ 关键信息打到 hilog 了吗？级别够吗？
□ 有没有一条"主动回传"的日志通道？（通道 ③）
□ 能不能用 curl 直接问服务？（通道 ④）
□ 我以为的判据，会不会是绿假信号？（hilog 缺失 / VmSize / 点击无反应）
```

**最后一句**：在受限平台上，"加日志"不是老土的做法 ——
**它是把"盲猜"变成"观测"的唯一手段**。先加可观测性，再改代码。
