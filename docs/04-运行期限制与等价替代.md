# 鸿蒙上的 5 个「Linux 有、这里没有」

> 把 Node 生态往鸿蒙上搬时，最花时间的不是崩溃，而是**"明明在 Linux 上跑得好好的"**。
> 这篇文章记录我实测到的 5 个差异，以及**每一个的等价替代**。
>
> **规律**：凡是靠"文件系统小技巧"实现**原子性/加锁**的地方
> （lockfile / hardlink / `O_TMPFILE` / `renameat2`…），在鸿蒙上**都要实测一遍** ——
> 但**都有等价替代**。

---

## 总览

| 能力 | 鸿蒙上的现象 | 等价替代 |
|---|---|---|
| `flock(2)` 文件锁 | `flock is not supported on openharmony-arm64` | 单进程场景**视为总是成功** |
| `link(2)` 硬链接 | `EACCES: permission denied, link '...tmp' -> '...final'` | 需独占 → `open(dst,'wx')` + 复制；已确认独占 → `rename` |
| spawn 外部程序 | `spawnSync → EACCES`（`/bin/sh` 存在但不可执行） | 用**纯 JS 复刻**该工具的输出契约 |
| `os.homedir()` | 指向沙箱外，`EPERM: opendir '/storage/Users/currentUser'` | 宿主壳里 `setenv("HOME", <沙箱内目录>)` |
| `childProcessManager` | `Capability not support. (code=801)` | 见 [第 2 篇](02-常驻与子进程的实测死法.md) |

---

## 一、`flock(2)`：整类锁文件机制失效

### 现象

```
flock is not supported on openharmony-arm64
```

很多 Node 生态用 `flock` 做**单实例互斥**（例如"同一份数据目录只能有一个进程"）。

### 替代

**单进程场景下直接视为"总是获取成功"。**

为什么这是安全的：鸿蒙 App 的沙箱模型本身就不允许同一个 App 起两个进程访问同一份沙箱数据，
所以那个锁**防的是不存在的场景**。硬要"报错"反而会让应用起不来。

```js
// 覆盖实现：在鸿蒙上把"加锁"变成恒成功
export async function flock(fd, mode) {
  if (process.platform === 'openharmony') return true;   // 单进程，无竞争
  return realFlock(fd, mode);
}
```

> **判断原则**：先问"这个锁在鸿蒙的进程模型下还要不要"，
> 再决定"是替换实现还是直接退化"。**别急着找一个 flock 的替代品** —— 可能根本不需要锁。

## 二、`link(2)`：硬链接被拒，影响"原子发布"

### 现象

```
EACCES: permission denied, link '/data/.../x.tmp' -> '/data/.../x.final'
```

这是 Node 生态里一个非常常见的**原子写入**模式：
**先写临时文件 → 用 `link()` 把它"原子地"发布成目标名**（因为 `link` 在目标已存在时会 `EEXIST`，
天然实现"独占创建"语义）。

### 替代

**分两种情况，语义要保住：**

```js
import { link, open, copyFile, rename } from 'node:fs/promises';

async function publishExclusive(tmpPath, dstPath) {
  try {
    // 首选：硬链接 —— 同时拿到"原子"与"独占"
    await link(tmpPath, dstPath);
    return;
  } catch (e) {
    if (e.code !== 'EACCES' && e.code !== 'EPERM' && e.code !== 'ENOSYS') throw e;
  }
  // 退路：用 'wx'（独占创建）保住 EEXIST 语义
  //   'wx' = O_CREAT | O_EXCL | O_WRONLY：目标已存在时抛 EEXIST，与 link 的语义一致
  const fh = await open(dstPath, 'wx');
  try {
    await fh.writeFile(await readFile(tmpPath));
  } finally {
    await fh.close();
  }
  await unlink(tmpPath).catch(() => {});
}

// 若调用方【已经确认目标不存在】，直接 rename 更省事（rename 在鸿蒙上可用）
async function publishOverwrite(tmpPath, dstPath) {
  await rename(tmpPath, dstPath);
}
```

**关键**：`open(dst, 'wx')` 是保住 `EEXIST` 语义的关键 ——
**不能简单退化成"写两次"**，那会把"独占"变成"后者覆盖前者"。

## 三、不能 spawn：依赖子进程的工具全部失效

### 现象

```
spawnSync('/bin/sh', ['-c', 'echo x'])  →  EACCES
```

**注意**：`/bin/sh` 和 `/system/bin/sh` **都存在**，`fs.existsSync` 返回 true ——
所以"先检查文件是否存在"这个判据**会误导你**。真正的判据是**执行一下**。

### 替代：复刻"输出契约"，不是复刻工具

这条最值得展开，因为**方法比结论重要**。

很多工具（`ripgrep`、`jq`、`fd`…）被 Node 生态当"子进程依赖"用。
在鸿蒙上它们全部不可用。**但你不必重写整个工具** ——
你要复刻的是**它与调用方之间的契约**。

**实例**：某框架的 `glob` / `grep` 工具内部 spawn `ripgrep`。
我的做法是**只复刻 `rg` 的输出格式**：

```
glob：argv = --files --glob=<p> --sort=modified --no-ignore --hidden [--glob=!**/x …] [-- <root>]
      ⇒ stdout = 换行分隔的路径，**按 mtime 升序**
      ⇒ 无命中时 exitCode = 0（正常返回空）

grep：argv = --json --regexp=<p> [--glob=<include>] [-- <root>]
      ⇒ stdout = NDJSON，只消费 {"type":"match","data":{path:{text},line_number,lines:{text}}}
      ⇒ **无命中时 exitCode = 1**（对应调用方的 noMatches 分支）

返回值形状：{ stdout, noMatches, workdir }
```

**为什么这样最省事**：调用方只认这几样东西。
复刻输出格式大约 100 行纯 JS；复刻 `rg` 本身是不可能的任务。

**方法论**：
> 把"需要子进程"的 CLI 工具移植到受限平台时，
> **先看它与你交互的输出契约，再决定复刻哪一层。**

### 两个必须注意的细节

1. **排序**：`glob` 契约要求**按 mtime 升序**，不是按字母序 —— 复刻时要显式排序。
2. **退出码语义**：`grep` 用**退出码 1** 表示"没有匹配"（`rg` 的历史行为），
   不是错误。**复刻时漏了这个，调用方会把它当失败。**

## 四、`os.homedir()` 指向沙箱外

### 现象

```
EPERM: opendir '/storage/Users/currentUser'
```

Node 的 `os.homedir()` 读 `$HOME`。鸿蒙 App 沙箱**读不到**用户的真实主目录。

很多框架的**文件选择器默认从 homedir 开始** ⇒ 一打开就 `EPERM`。

### 替代

**在宿主壳（native 侧）把 `HOME` 指到沙箱内可读可写的目录：**

```c
// 例如指向 dataDir 的父目录（即 <filesDir>）
std::string homeDir = ctx->dataDir;
const size_t slash = homeDir.find_last_of('/');
if (slash != std::string::npos && slash > 0) homeDir = homeDir.substr(0, slash);
::setenv("HOME", homeDir.c_str(), 1);
::setenv("USERPROFILE", homeDir.c_str(), 1);   // Windows 习惯的变量名，一并设上无害
```

**效果**：文件选择器能正常浏览沙箱内目录。

**⚠ 边界要说清**：这只是让**应用自己的目录**可用；
**读手机上的用户文件仍然要靠系统文件选择器授权**（另一套 API，见下）。

## 五、读用户文件：系统文件选择器（这条是可行的）

与上面四条不同，这条**有正规通路**，但模式语义容易踩错。

### 读文件（实测可用 ✓）

`DocumentSelectMode.FILE` 或 `MIXED`，然后用 `fs.openSync(uri)` 拿 fd，
再 `fs.copyFileSync(fd, 沙箱内路径)`。实测成功导入过 **149 MB** 的文件。

```ts
const picker = new picker.DocumentViewPicker();
const uris = await picker.select({ maxSelectNumber: 1,
  fileSuffixFilters: ['.zip', '.json', '.txt'] });
const file = fs.openSync(uris[0], fs.OpenMode.READ_ONLY);
fs.copyFileSync(file.fd, sandboxPath);      // 关键：拷进沙箱，Node 才能读
fs.closeSync(file);
```

**★ 必须拷贝进沙箱** —— 因为 Node 读的是文件系统路径，
而选择器给的是 URI（`file://...`），且落在沙箱外。

### 选文件夹：目前没打通 ✗

| 模式 | 点一个文件夹行的行为 | 结果 |
|---|---|---|
| `MIXED`（多选） | **进入该目录** | 「完成」时若未选任何项 ⇒ 空操作，promise 不返回 |
| `FOLDER` | **高亮选中** | 但导航手势与 `MIXED` 不同，坐标对不上 |

**更麻烦的是**：选择器是**独立系统窗口**，UI 自动化的 `dumpLayout` **时有时无**（时序相关）。

**⇒ 建议**：优先用**文件导入**（可靠）；确实需要整目录时，让用户**多选文件**，
或把这一步留给用户手动点（程序只负责后续复制）。

## 一张判据表：别用"看起来能用"当判据

| 判据 | ❌ 会被骗 | ✅ 应该这样验 |
|---|---|---|
| 文件存在 | `existsSync('/bin/sh')` → true，但不可执行 | **执行一下**看 `EACCES` |
| 路径可用 | `fs.accessSync` 对 0 字节文件/目录也返回 true | 判 `isFile() && size > 阈值` |
| API 可用 | 声明文件里有 = 存在 ≠ 可用 | **真机调一次**（801 的教训） |
| 写入成功 | 写完了，但读的人读不到 | **让最终使用者去读一遍**（谁写谁读） |
| 压缩生效 | HAP 变小了 | **读 zip 中央目录**看 compress_type |

**这五条我都踩过。** 它们的共同点是：**"能构建/能写入/能返回"都不等于"能运行/能读取/能用"。**
