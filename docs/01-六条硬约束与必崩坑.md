# 在鸿蒙 App 里嵌入真正的 Node.js：6 条硬约束、9 个必崩坑与实测数据

> 平台：HarmonyOS / OpenHarmony，`arm64`，API 26
> 实测机型：Mate 70（HarmonyOS 7）
> 实测结论：**`platform: openharmony`、`node v24.2.0` 在 App 进程内成功运行，端上 HTTP 服务可被 ArkWeb 加载**
> 关键词：`dlopen` · `PT_INTERP` · `io_uring` SIGSYS · `--jitless` · `APP_INPUT_BLOCK` · `require-builtin`

---

## 0. 为什么这件事值得写

鸿蒙上跑 Node 的教程大多是两种：

1. **"用 childProcess"** —— 在这台设备上直接不可用（见第 6 节 801 实测）；
2. **"把 node 可执行文件塞进 HAP 然后 spawn"** —— 会在更严格的 seccomp 下被杀（见第 3 节第 5 条）。

真正能上生产的形态是**进程内 `dlopen` + `node::Start`**。而这条路有 **6 个硬约束**，
违反其中任何一个，症状都**不是报错，而是崩溃或静默失败**——最贵的那种 bug。

下面每一条都是真机上花掉的时间换来的，附**验证命令**与**期望输出**，可复现。

---

## 1. 架构（已验证可用）

```
ArkTS UI
 └─ NAPI 模块 libnode_ctl.so（C++，随包编译）
     ├─ 必须在【detached 线程】里做事（UI 线程做 dlopen 会 APP_INPUT_BLOCK）
     ├─ 装 SIGSYS shim（把 io_uring_setup 的 seccomp trap 转成"正好 -1"）
     ├─ 装崩溃处理器（backtrace 写文件 + 打 hilog）
     ├─ setenv("UV_USE_IO_URING","0")   ← 必须在 libuv 初始化前
     └─ dlopen("libnode.so")
         → dlsym("_ZN4node5StartEiPPc")   ← 真实导出符号，别猜
         → node::Start(argc, argv)
```

**HAP 布局**

```
entry/libs/arm64-v8a/libnode.so          ← Node 运行时（真共享库）
entry/libs/arm64-v8a/libnode_ctl.so      ← NAPI 胶水（进程内启动）
entry/libs/arm64-v8a/libc++_shared.so    ← 必须一起打进去（见第 2 节）
entry/src/main/resources/rawfile/        ← JS 载荷（见第 3 节第 4 条）
<filesDir>/<app>-data/                   ← 可变状态（DSH_HOME）
```

## 2. 六条硬约束（违反其一就起不来）

### ① `libnode.so` 必须是**真共享库**，不能是 PIE

这是最容易死人、且症状最迷惑的一条。

网上能下到的 `libnode.so`（例如各种 `ohos-node` 的 release）**很多是 PIE 可执行文件**：
`ET_DYN` 看起来对，但它带 `PT_INTERP`。把它 `dlopen` 进鸿蒙 App，会**把 local-exec 的 `%fs`
TLS 别名到宿主 App 的 TLS 块**，于是 V8 的 `thread_local current_per_thread_assert_data`
**读到垃圾值**，release 版 `CHECK AllowHeapAllocationInRelease` 在 `Isolate::Initialize`
的**第一次堆分配就触发崩溃**。

**验证（必做，下载后立刻做）**

```bash
llvm-readelf -h libnode.so | grep -E 'Type|Machine'
# 期望：Type: DYN    Machine: AArch64

llvm-readelf -l libnode.so | grep -c INTERP
# 期望：0        ← 【有 PT_INTERP 就是 PIE，dlopen 必崩】
```

**取证结论**：自己构建时必须带 `--shared`（产出 PIC + 动态 TLS + SONAME）：

```bash
export CC="$SDK/llvm-19/llvm/bin/aarch64-unknown-linux-ohos-clang   -fno-emulated-tls"
export CXX="$SDK/llvm-19/llvm/bin/aarch64-unknown-linux-ohos-clang++ -fno-emulated-tls"

./configure --dest-cpu=arm64 --cross-compiling \
  --shared --without-npm --without-corepack \
  --v8-disable-temporal-support        # ★ OHOS 交叉编译不开这个构建会失败
make -j$(nproc)
```

> 内存坑：Node 构建（链接 + V8 `mksnapshot`）在 **2 vCPU / 1.6 GB 无 swap** 的机器上极可能 OOM。
> 先 `fallocate -l 4G /swap && mkswap /swap && swapon /swap` 再编译。

### ② `libc++_shared.so` 必须一起进 HAP

漏了它的症状**不是报错**：`dlopen` 失败，**ArkTS 侧拿到 `undefined`**。
你会以为是"类型声明没接上"，实际是缺库。

```bash
llvm-readelf -d libnode.so | grep NEEDED
# 期望含：libc++_shared.so, libc.so
```

从 NDK 取：`native/llvm/lib/aarch64-linux-ohos/libc++_shared.so`。

### ③ `argc` 不能把 argv 末尾的 `nullptr` 哨兵算进去

多算一个 ⇒ Node 拿到 `NULL` 参数 ⇒ **5 毫秒内段错误**。

这个 bug 是靠**打印自己的 argv** 抓到的，一行日志就暴露了：

```c
for (int i = 0; i < argc; i++) LOG("argv[%d]=%s", i, argv[i] ? argv[i] : "(null)");
// 看到 argv[N]=(null) ⇒ argc 多了一个
```

**结论：把"打印自己的入参"当成默认动作，不要省。**

### ④ JS 载荷走 `rawfile` + `resourceManager`，别依赖 `resfile` 路径

实测：`resfile/` 里的文件**连 ArkTS 的 `fs` 都访问不到**（`No such file or directory`）；
就算能读，Node 的 **musl 裸 `open()` 也读不到 HAP 内部路径**。

正确做法：

```
ArkTS: resourceManager.getRawFileContentSync('payload.tar.gz') → 字节
       → fs.writeSync 写入 filesDir
       → 把【真实的文件系统路径】交给 Node
```

**★ 而且必须"让最终使用者也当写入者"** —— 见下面第 3 节第 4 条的实测。

### ⑤ `--expose-internals` 必需，但它能帮你**免掉全部原生模块移植**

`internal/modules/*` 没有这个 flag 会**全部** `MODULE_NOT_FOUND`（实测 5/5 失败）。

好消息：官方那条原生插件路径**本来就有纯 Node 兜底，而且被 try/catch 包住**：

```js
// cordis-plugin-loader 的真实代码
if (process.execArgv.includes("--expose-internals"))
    try { return require(id); } catch {}                                  // ★ 纯 Node 路径
try { return require("node-addon-require-builtin").requireBuiltin(id); } catch {}
```

所以**一个 ~20 行的 JS 桩 + 启动参数带 `--expose-internals`**，就能彻底替代原生插件：

```js
// node-addon-require-builtin 的纯 JS 桩
module.exports = {
  requireBuiltin: (id) => require(id),
  isAllowedInternalId: () => true,
};
```

**实测**：5 个内部模块（`internal/modules/{esm/loader,cjs/loader,helpers,esm/utils,esm/resolve}`）
**13/13 全通过**；去掉 flag 则 5/5 全失败。
这 5 个模块在 Node v24.2.0 里**全部存在** ⇒ 版本差 24.2 vs 24.18 **不影响**这条路。

> **⇒ 原生移植工作量 = 0。** 这是整个方案里最后一块风险，已从"推断"变成"实测"。

### ⑥ 同一进程内 `node::Start` 只能调用一次

第二次会命中 `node.cc:827`：`Assertion failed: limit_called.exchange(true)`。

**所以不要设计"进程内自动重启"**。要重试就提示用户杀掉应用重开，或改用子进程形态
（而子进程在这类设备上又不可用，见第 6 节 ⇒ 现实的答案是**让用户重开**）。

## 3. 还有 5 个坑，症状比原因更迷惑

### 1. `node::Start` 里 SIGTRAP：`Check failed: 12 == (*__errno_location())`

**真因**：V8 运行时要做 `PROT_EXEC` 映射，**OpenHarmony 的 W^X 策略拒绝**。
**修法**：启动参数加 **`--jitless`**。同批建议带 `--no-verify-heap`。

> ⚠ **但 `--jitless` 会关掉 WebAssembly**。如果业务用到 `fetch`（Node 内置 undici 的 llhttp 是 WASM）
> 就会启动即崩。**先不带 `--jitless` 试一次** —— 实测部分设备根本不需要它（无 SIGTRAP）。
> 只用 `node:http`（原生 llhttp）的应用看不出这个差别，**很容易误判为"偶发"**。

### 2. libuv 在 loop init 就崩

**真因**：libuv 初始化时**无条件**探测 `io_uring_setup(425)`，**沙箱 seccomp 会 trap 它**。

**修法**：装 SIGSYS shim，把 trap 转成 **`-1`**
—— **必须正好是 `-1`，不是 `-ENOSYS`**，libuv 的守卫才认。
同时 `setenv("UV_USE_IO_URING", "0")`，**且必须在 libuv 初始化之前**。

### 3. 启动即 ANR：`APP_INPUT_BLOCK`

**真因**：`dlopen` / `node::Start` 跑在 **ArkTS UI 线程**，阻塞超过看门狗阈值。
**修法**：开一个 **detached bootstrap 线程**去做 `dlopen` + `node::Start`。

### 4. ★ "同目录、同进程、同 uid，ArkTS 写的文件 Node 能读，鸿蒙解压器写的 Node 读不到"

这是最反直觉的一条，也是最贵的一条。

| 场景 | 写入者 | Node 能否 `require` |
|---|---|---|
| 简单入口脚本 | ArkTS `fs.writeSync` | ✅ **能** |
| 解包后的业务载荷 | OHOS `zlib.decompressFile` | ❌ **不能**（`MODULE_NOT_FOUND`，`requireStack: []`）|

**证据**：ArkTS 侧 `statSync` 明明看到 11237 字节、`isFile=true`。

**正解：让最终使用者也当写入者。** 把 JS 载荷打成**单个 `tar.gz`** 放 `rawfile/`，
由端上 **`bootstrap.js` 用 Node 自己的 `zlib` + `fs` 解包**：

```js
// bootstrap.js（约 30 行）
const zlib = require('zlib'), fs = require('fs'), path = require('path');
const [tarGz, dest] = process.argv.slice(2);
const buf = zlib.gunzipSync(fs.readFileSync(tarGz));
// 极简 tar 解析：512 字节头 + 路径前缀，比 zip 简单得多（zip 要中央目录 + deflate 分支）
for (let off = 0; off + 512 <= buf.length; ) {
  const header = buf.subarray(off, off + 512);
  const name = header.subarray(0, 100).toString('utf8').replace(/\0.*$/, '');
  if (!name) { off += 512; continue; }
  const size = parseInt(header.subarray(124, 136).toString('utf8').replace(/\0.*$/, '').trim(), 8) || 0;
  const type = String.fromCharCode(header[156]);
  const full = path.join(dest, name);
  off += 512;
  if (type === '5') { fs.mkdirSync(full, { recursive: true }); continue; }
  if (!size) continue;
  fs.mkdirSync(path.dirname(full), { recursive: true });
  fs.writeFileSync(full, buf.subarray(off, off + size));
  off += Math.ceil(size / 512) * 512;
}
require(path.join(dest, 'node_modules/@deepseek-ai/dsh/lib/bin.js'));
```

**为什么用 tar 不用 zip**：tar 只需解析 512 字节头，**约 30 行纯 JS**；
zip 要中央目录 + deflate/存储分支，代码量大得多。Node 内置 `zlib` 直接吃 `.tar.gz`。

### 5. `.so` / `.node` 没签名，装上也用不了

鸿蒙商用版对 ELF 做**代码签名校验**，没有 `.codesign` section 直接不可用。
用 OHOS 工具链的 `binary-sign-tool` 自签，**注意要签在 `strip` 之后**。

## 4. 五个"在别处一定会踩、而且搜不到答案"的运行时限制

这些是鸿蒙与 Linux 的实际差异，`fs` 小技巧全都得实测：

| 限制 | 报错原文 | 等价替代 |
|---|---|---|
| `flock(2)` 不支持 | `flock is not supported on openharmony-arm64` | 单进程场景**视为总是获取成功** |
| `link(2)`（硬链接）被拒 | `EACCES: permission denied, link '...tmp' -> '...final'` | 需独占 → `open(dst,'wx')` + 复制；已确认独占 → `rename` |
| `os.homedir()` 指向沙箱外 | 文件选择器 `EPERM: opendir '/storage/Users/currentUser'` | 宿主壳里 `setenv("HOME", <沙箱内目录>)` |
| **seccomp 禁止执行任何外部程序** | `glob`/`grep` 依赖的 ripgrep `spawnSync` → `EACCES`（`/bin/sh` 存在但不可执行） | 用**纯 JS 复刻** CLI 的输出契约（见下） |
| `childProcessManager` 返回 801 | `Capability not support. (code=801)` | **本机不支持**，见第 6 节 |

**规律**：凡是用"文件系统小技巧"实现原子性/加锁的地方
（lockfile / hardlink / `O_TMPFILE` / `renameat2` …），在鸿蒙上**都要实测一遍**，
但**都有等价替代**。

### 纯 JS 复刻 ripgrep 的教训（很有代表性）

`glob` / `grep` 都 spawn ripgrep，而鸿蒙 **seccomp 禁止 app 执行外部程序**，
且 `@vscode/ripgrep` 包里**根本没有二进制**。

**做法不是"复刻整个工具"，而是复刻"它与你交互的输出契约"**：

```
glob：argv --files --glob=<p> --sort=modified --no-ignore --hidden [--glob=!**/x …] [-- <root>]
      ⇒ stdout = 换行分隔路径，【按 mtime 升序】

grep：argv --json --regexp=<p> [--glob=<include>] [-- <root>]
      ⇒ stdout = NDJSON，只消费 {"type":"match","data":{path:{text},line_number,lines:{text}}}
      ⇒ 【无命中时 exitCode=1】（对应 noMatches）

返回值：{ stdout, noMatches, workdir }
```

> **教训**：把"需要子进程"的 CLI 工具移植到受限平台时，
> **先看它与你的输出契约，再决定复刻哪一层** —— 复刻 `rg` 的输出格式比复刻整个工具简单得多。

## 5. 开发期最大的敌人不是崩溃，是**看不见**

三条通道缺一不可，每加一条，定位速度上一个台阶：

| 通道 | 命令 | 用途 |
|---|---|---|
| **看屏幕** | `hdc shell snapshot_display -f /data/local/tmp/s.jpeg` + `hdc file recv` | 自己看 UI 状态 |
| **点按钮** | `hdc shell uitest uiInput click <x> <y>` | 自己操作 UI |
| **回传日志** | `hdc rport tcp:19999` + 端上 POST 到 `127.0.0.1:19999` | **完整不截断**的日志 |

### ★ 一个会让所有人浪费几小时的假象

**沙箱里的日志文件，连 debug 签名也不让 `hdc` 读**（实测 `permission denied`）。

所以：

1. **native 侧关键信息必须同时打 `hilog`**（崩溃处理器里也要打 —— 虽然信号上下文不严格安全，
   但那是唯一出路）；
2. **把界面当调试台**：把 `typeof 模块`、状态、`node-boot.log` / `node-stdout.log` 的**尾部**
   直接刷到 UI 上，**一张截图胜过十次盲猜**；
3. 应用侧 INFO 日志**常不进 hilog dump 缓冲** —— 别以为"没日志=没执行"。

### 两个"别用感觉判断"的例子

- **日志面板会截断长数字**：`36,305,644` 被显示成 `3,630,564` —— 差点据此误判。
  ⇒ 打体积用 `MB` 保留一位小数，或分段打印。
- **别拿 `VmSize` 当"V8 起来了"的证据**：ArkTS/ArkWeb 自己就占 **40 GB** 虚拟地址空间。

### 布局是你最可靠的判据

判断"某个点击是否生效"，**最可靠的是前后两次 `dumpLayout` 的差异**，不是截图也不是猜坐标：

```
点击前 / 点击后各 dumpLayout 一次 → 对比节点坐标与数量
布局一字未变 ⇒ 这个点击无效（我踩过：界面上一个"标签"点了没反应）
```

**并且：带确认按钮的对话框，先找"确定/打开/完成"，不要用系统返回键** ——
Back 通常只表示"取消/关闭"，**不等于确定**。用 Back 关掉窗口后，界面会一直停在原状态，
**表现为"发了消息完全不动"**，极易误判成后端故障。

## 6. 两条"API 存在但设备不支持"的实测定论

鸿蒙很多新能力是**"SDK 里有声明、具体设备未实现"** ——
**看声明文件只能证明它"存在"，不能证明它"可用"**。必须真机试一次。

### ① `childProcessManager` → 801

| 层次 | 结论 |
|---|---|
| API 是否存在 | **存在**（`@ohos.app.ability.childProcessManager`，含 `startNativeChildProcess`）|
| **这台设备是否支持** | ✗ **不支持** —— `startArkChildProcess` 返回 `Capability not support. (code=801)`，hilog 里**完全没有子进程入口日志** |
| 能力结论 | ✗ "把 Node 放进子进程 ⇒ 崩了能重启"与"进程外看门狗"**在这台设备上做不到** |

> **801 在本项目里含义统一**：`getUserDownloadDir()` / `getUserDocumentDir()` → 801；
> 权限 `authResults=[2,2]`（2 = 不受支持）。
> **⇒ 设计时不要把"崩溃自动重启"当默认能力。**

### ② 后台常驻：普通应用做不到无限常驻

实测三个错误码，都很明确：

| 尝试 | 结果 |
|---|---|
| `requestSuspendDelay(reason, cb)` | **可用** —— 把切后台后的可用时间从约 90 秒延长到 **3~4 分钟**；成本极低，值得保留 |
| `startBackgroundRunning(ctx, TASK_KEEPING, agent)` | **9800005** `Current device can not request continuous tasks of the TASK_KEEPING type` ⇒ 本机不支持该类型 |
| `startBackgroundRunning(ctx, DATA_TRANSFER, agent)`（无配套扩展）| **9900002** `Request is not allow after the preset time of entering background` ⇒ **进入后台超时后不允许再申请** |

**结论**：
1. 普通应用**无法无限常驻后台** —— 真正常驻必须实现 `ContinuousTaskExtensionAbility`（配套扩展能力）；
2. **要申请长时任务，必须在【进入后台之前】申请**（9900002 的教训）；
3. 最可靠的"常驻"是**把 App 保持在前台**；可用 `power-shell timeout -o <ms>` 覆盖熄屏时间。

## 7. 打包：HAP 从 151.6 MB 压到 71.8 MB（-53%）

### ★ `compressNativeLibs` 必须写在 `module.json5` 的 **module 级**

我在这上面踩了三次：

- 写进 `build-profile.json5` 的 `buildOption` ✗
- 写进 `buildOption.nativeLib` ✗
- 两者都被 schema 拒绝，报 `Schema validate failed`，**但不告诉你正确位置**

**正确写法（`entry/src/main/module.json5`）**：

```json5
{
  "module": {
    "pages": "$profile:main_pages",
    "compressNativeLibs": true,
    "extractNativeLibs": true
  }
}
```

**实测效果**

| 条目 | 压缩前 | 压缩后 |
|---|---|---|
| `libnode.so` | 120.9 MB | **43.0 MB**（DEFLATE，压到 1/2.8）|
| `libc++_shared.so` | 1.2 MB | 0.4 MB |
| `dsh-payload.tar.gz` | 28.1 MB | 28.1 MB（本身已 gzip，无空间）|
| **HAP 总大小** | **151.6 MB** | **71.8 MB** |

并且验证过：安装后系统会解压 `.so`，`dlopen` 照常工作 ⇒ **"能不能上架"级别的一项优化**。

> **方法论**：鸿蒙的 schema 校验只报"哪个键不对"，**不报"该写到哪"**。
> 遇到 `Schema validate failed` 时，去 `toolchains/configcheck/configSchema_rich.json`
> 或 `toolchains/modulecheck/module.json` 里**搜该键，看它出现在哪个对象下** —— 比猜快得多。

### 另外两个打包事实

- **hvigor 会排除点文件**：磁盘 11419 个 → HAP 11337 个，少的 82 个全是
  `.history` / `.github` / `.npmignore` / `.travis.yml` 之类 ⇒ **合理行为，无害**。
  **但核对时要直接查 HAP，不要只看磁盘。**
- **`llvm-strip` 对 Node 官方产物收益为 0**（已预 strip），别浪费时间。

## 8. 收尾：一张排障速查表

| 现象 | 真因 | 修法 |
|---|---|---|
| `dlopen` 成功但 `dlsym` 全 return null | 符号名靠猜 | 用 `llvm-nm` 读**真实二进制**的导出符号（`_ZN4node5StartEiPPc`），别用合成对象文件推断 |
| `node::Start` 里 SIGTRAP `Check failed: 12 == (*__errno_location())` | V8 `PROT_EXEC` 被 W^X 拒绝 | 启动加 `--jitless` |
| libuv 在 loop init 就崩 | `io_uring_setup` 被 seccomp trap | SIGSYS shim 转成**正好 `-1`** + `UV_USE_IO_URING=0` |
| 启动即 ANR `APP_INPUT_BLOCK` | `dlopen`/`node::Start` 在 UI 线程 | 开 **detached 线程** |
| ArkTS 报 `arkts-no-any-unknown` | 原生模块类型没接上 | `oh-package.json5` 加 `file:` 依赖 + **跑一次 `ohpm install`** |
| HAP 里没有 `libs/` | native 产物落在 `build/` | CMake 设 `CMAKE_LIBRARY_OUTPUT_DIRECTORY` → `entry/libs/<abi>/` |
| `dlopen` 失败、ArkTS 侧拿到 `undefined` | 缺 `libc++_shared.so` | 一起打进 HAP |
| Node 拿到 NULL 参数、5 ms 段错误 | `argc` 把 argv 末尾 `nullptr` 算进去了 | 打印 `argv[i]` 核对 |
| `MODULE_NOT_FOUND`（解包后的文件） | 写入者是鸿蒙解压器 | 改由 **Node 自己解包**（bootstrap.js）|
| `internal/modules/*` 全部 `MODULE_NOT_FOUND` | 缺 `--expose-internals` | 加 flag + 20 行 JS 桩 |
| 第二次启动 node 断言失败 | `node::Start` 一进程只能一次 | 不做进程内重启 |
| 商用机报签名问题 | ELF 无 `.codesign` | `binary-sign-tool` 自签（**strip 之后**）|
